# Guildhall 0.13.0 / Narrative Harness Acceptance Gap

Date: 2026-07-19
Status: not accepted
Scope: the current 0.13.0 release-loop acceptance against the Narrative
Harness MVP shipping objective

## User job

A release acceptance run must prove both sides of the release loop:

1. Guildhall shows one authoritative, exact-scope release state across its
   API, CLI, UI, restart, and release surfaces.
2. Narrative Harness has actually produced the runnable MVP artifacts that
   Guildhall claims to have shipped.

The second proof cannot be inferred from completed Guildhall tasks or from a
generic build.

## Highest-risk gap

Before this audit fix, `scripts/release-acceptance-audit.mjs` never read the
Narrative Harness checkout. It could pass the Guildhall-side release checks
even if `runs/proof/mvp.json` and the live model-bakeoff artifact were absent,
offline-only, or explicitly in a `no-eligible-candidate` state.

That made the acceptance document's phrase “Narrative Harness release-cycle
proof” materially stronger than its executable evidence. The missing boundary
was between Guildhall's durable release projection and Narrative Harness's
durable product proof artifacts.

## Narrow fix applied

Added `scripts/narrative-harness-release-proof.mjs` and its focused Vitest
coverage. The existing acceptance command now discovers the sibling Narrative
Harness checkout (or uses
`GUILDHALL_ACCEPTANCE_NARRATIVE_HARNESS_ROOT`) and validates:

- PNPM scripts for build, typecheck, proof, MVP execution, and model bakeoff;
- the complete intent-to-review MVP stage chain and selected release label;
- provider-backed MVP execution, model invocations, evaluation, reviewer
  coverage, bounded context, and essential-history retention;
- live bakeoff fixture coverage, reviewer-lens coverage, explicit job outcome
  records, eligible model selection, quality/safety gates, complete cost
  evidence, and adult-compatible fixture completion.

This is read-only acceptance tooling. It does not change project state, task
schemas, release schemas, projections, or provider behavior.

## Current evidence

Command:

```sh
pnpm audit:release-acceptance
```

Current installed-service result after the gate was added: **66 checks, 12
failed**.

The Guildhall-side failures are real and must remain visible:

- the selected release reports `16` items, `15` done, and `1` blocked;
- Overview and Release readiness report `blocked` / `work_remaining`;
- the durable release field still says `shipped`, which contradicts the current
  unfinished scope;
- the fleet projection reports Narrative Harness summary error because its
  payload exceeds the `16 KiB` fleet-card bound;
- the CLI reports `16` included items rather than the stale acceptance note's
  `15`.

The new Narrative Harness proof failures are also real:

- `runs/proof/mvp.json` is `offline-fixture`, has
  `modelQualityClaim: not_proven_offline`, and records zero model invocations;
- the live bakeoff decision is `no-eligible-candidate`;
- no selected model clears the quality/safety gates;
- no selected model has complete cost evidence;
- therefore no selected model has an adult-fixture completion record that can
  satisfy the release gate.

The checked-in Kimi artifact does prove authentication, bounded job execution,
adult-fixture non-refusal, and honest failure classification. It does **not**
prove a shippable model decision. The gate deliberately preserves that
distinction.

## Exact evidence required to clear the gap

1. Repair or supersede the current Guildhall selected release so its saved
   membership, task state, lifecycle, readiness, CLI, and all UI/API surfaces
   agree on the actual current release. A `shipped` field cannot coexist with
   unfinished selected work.
2. Produce a provider-backed Narrative Harness MVP artifact from the selected
   model, with the complete stage chain, at least the synopsis/story-record/
   chapter-draft invocations, passing evaluation, and compact history.
3. Run the bounded live bakeoff with current provider prices supplied. The
   artifact must contain a provisional winner whose drafting/review gates,
   adult-compatible fixture, failure records, latency, and cost evidence all
   pass.
4. Rebuild, install, stop/start, verify `/api/stale-server`, and rerun this
   acceptance command against the same saved release and proof artifacts.
5. Attach fresh installed-app desktop/mobile screenshots for the accepted
   routes and claims. Existing geometry checks are useful, but they are not a
   substitute for visible release-state proof.

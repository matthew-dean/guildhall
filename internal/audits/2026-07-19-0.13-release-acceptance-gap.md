# Guildhall 0.13.0 / Narrative Harness Acceptance Gap

Date: 2026-07-19
Status: not accepted
Scope: the current 0.13.0 release-loop acceptance against the Narrative
Harness MVP shipping objective

## User job

A release acceptance run must prove both sides of the release loop:

1. Guildhall shows one authoritative, exact-scope release state across its
   API, CLI, UI, restart, and release surfaces.
2. Narrative Harness has actually produced the runnable MVP artifacts that
   Guildhall claims to have shipped.

The second proof cannot be inferred from completed Guildhall tasks or from a
generic build.

## Highest-risk gap

Before this audit fix, `scripts/release-acceptance-audit.mjs` never read the
Narrative Harness checkout. It could pass the Guildhall-side release checks
even if `runs/proof/mvp.json` and the live model-bakeoff artifact were absent,
offline-only, or explicitly in a `no-eligible-candidate` state.

That made the acceptance document's phrase “Narrative Harness release-cycle
proof” materially stronger than its executable evidence. The missing boundary
was between Guildhall's durable release projection and Narrative Harness's
durable product proof artifacts.

## Narrow fix applied

Added `scripts/narrative-harness-release-proof.mjs` and its focused Vitest
coverage. The existing acceptance command now discovers the sibling Narrative
Harness checkout (or uses
`GUILDHALL_ACCEPTANCE_NARRATIVE_HARNESS_ROOT`) and validates:

- PNPM scripts for build, typecheck, proof, MVP execution, and model bakeoff;
- the complete intent-to-review MVP stage chain and selected release label;
- provider-backed MVP execution, model invocations, evaluation, reviewer
  coverage, bounded context, and essential-history retention;
- live bakeoff fixture coverage, reviewer-lens coverage, explicit job outcome
  records, eligible model selection, quality/safety gates, complete cost
  evidence, and adult-compatible fixture completion.

This is read-only acceptance tooling. It does not change project state, task
schemas, release schemas, projections, or provider behavior.

## 2026-08-07 release path and artifact automation repair

Current 0.13.0 release posture:

1. The blocker remains the saved Guildhall selected-release contradiction:
   the release cannot be both `shipped` and have unfinished selected work.
   Repair or supersede that selected release through the project-state path,
   not by hiding the count or mutating read-time projections.
2. The Narrative Harness proof artifacts and bounded live bakeoff are accepted
   as executable evidence for this gate, with Kimi K3 still only a provisional
   contract-level winner until the separate semantic craft assessment is done.
3. After release-state repair, run the installed acceptance sequence again:
   `pnpm build`, `pnpm dev:install`, `guildhall stop && guildhall start`,
   `/api/stale-server`, and `pnpm audit:release-acceptance`.
4. Attach fresh installed-app desktop/mobile route screenshots and API/CLI
   readback to this audit before calling 0.13.0 ready.

Release artifact automation was also tightened because the 0.12.0 package and
docs shipped while the remote Git tag and GitHub Release artifact did not line
up. `scripts/publish.mjs` now pushes the release branch and `v<version>` tag by
default after the real publish commits, verifies the remote tag, and leaves a
`--no-push` escape hatch for intentionally staged releases. The tag push is the
event that runs `.github/workflows/release.yml` and creates
`guildhall-macos.tar.gz` plus its checksum.

For the existing 0.12.0 backfill, push the local `v0.12.0` tag only after
confirming the local tag points at the accepted release commit:

```sh
git rev-parse v0.12.0
git push origin refs/tags/v0.12.0
```

That should trigger the same GitHub release artifact workflow without
republishing npm.

## Current-State Release Repair Decision

- Work id: `release-authority-boundary-2026-07-19`.
- Touched contracts: the normalized `release_membership` write boundary, the
  `ProjectRelease` lifecycle invariant for `shipped`, and the saved fleet-card
  projection.
- Rule: an existing shipped release keeps its lifecycle and included/deferred
  membership. Ordinary task, batch, snapshot, and release-selection writes
  reject additions, removals, lifecycle changes, and reopening completed work;
  new work must use a later release. The fleet card stores bounded identity,
  counts, release truth, and IDs/routes for detail, without copying giant task
  text.
- Considered but not touched: release-readiness math, CLI formatting, UI
  detail routes, the Narrative Harness queue, and historical data repair.
  Existing invalid state is surfaced for explicit re-intake rather than
  silently rewritten on read.
- Persisted schema touched: none. The existing normalized release table and
  existing fleet projection table remain the authorities; no migration id or
  compatibility reader is added.
- Proof required: all current-state writers must reject an invalid shipped
  release mutation before replacing data, and every fleet publication path must
  keep an oversized task prompt out of the bounded fleet payload.
- Proof provided: `release-lifecycle.test.ts`, the project-state database
  boundary test, the fleet read-model oversized-prompt test, focused suite
  (86 passing), `pnpm typecheck`, and `pnpm lint:contracts`.
- Apply/revert: source-only change; no current project data is changed by this
  fix. A later explicit Narrative Harness re-intake may repair the existing
  shipped-release contradiction.

# Guildhall 0.13.0 / Narrative Harness Acceptance Gap

Date: 2026-07-19
Status: accepted on 2026-08-07
Scope: the current 0.13.0 release-loop acceptance against the Narrative
Harness MVP shipping objective

## User job

A release acceptance run must prove both sides of the release loop:

1. Guildhall shows one authoritative, exact-scope release state across its
   API, CLI, UI, restart, and release surfaces.
2. Narrative Harness has actually produced the runnable MVP artifacts that
   Guildhall claims to have shipped.

The second proof cannot be inferred from completed Guildhall tasks or from a
generic build.

## Highest-risk gap

Before this audit fix, `scripts/release-acceptance-audit.mjs` never read the
Narrative Harness checkout. It could pass the Guildhall-side release checks
even if `runs/proof/mvp.json` and the live model-bakeoff artifact were absent,
offline-only, or explicitly in a `no-eligible-candidate` state.

That made the acceptance document's phrase “Narrative Harness release-cycle
proof” materially stronger than its executable evidence. The missing boundary
was between Guildhall's durable release projection and Narrative Harness's
durable product proof artifacts.

## Narrow fix applied

Added `scripts/narrative-harness-release-proof.mjs` and its focused Vitest
coverage. The existing acceptance command now discovers the sibling Narrative
Harness checkout (or uses
`GUILDHALL_ACCEPTANCE_NARRATIVE_HARNESS_ROOT`) and validates:

- PNPM scripts for build, typecheck, proof, MVP execution, and model bakeoff;
- the complete intent-to-review MVP stage chain and selected release label;
- provider-backed MVP execution, model invocations, evaluation, reviewer
  coverage, bounded context, and essential-history retention;
- live bakeoff fixture coverage, reviewer-lens coverage, explicit job outcome
  records, eligible model selection, quality/safety gates, complete cost
  evidence, and adult-compatible fixture completion.

This is read-only acceptance tooling. It does not change project state, task
schemas, release schemas, projections, or provider behavior.

## Flow Audit Finding: mobile project ticker overflow

- Work id: `0.13-release-mobile-project-ticker-overflow`.
- User job: a mobile user opening Overview, Map, Work, or Release can read the
  selected-release ticker without hidden horizontal overflow and still tell
  what is happening now, what is queued, what is blocked, what they can do
  next, and whether the system is working.
- Finding: the shared `project-ticker-actor` span rendered the selected release
  label as `flex:none`. On Narrative Harness mobile routes the label measured
  `447px` in a `390px` viewport. The document scroll width stayed `390px`, so
  the route looked stable while the text itself protruded past the right edge.
- Correction: `ProjectView.svelte` lets the ticker main row flex, lets the
  actor shrink/wrap, and on narrow viewports gives the actor its own wrapped
  row. The release label remains visible instead of clipped.
- Calibration: `internal/calibration/cases/ux/hidden-horizontal-overflow.yaml`
  now includes this mobile ticker miss as a concrete production example.
- Proof provided: installed Playwright geometry readback for mobile Overview,
  Map, Work, and Release at `390x844` showed `clientWidth:390`,
  `scrollWidth:390`, and `overflowingCount:0` on every route; the full
  acceptance audit dropped from `23` failures to `19`.

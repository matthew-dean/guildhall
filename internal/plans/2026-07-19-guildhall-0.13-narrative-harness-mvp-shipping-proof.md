# Guildhall 0.13.0: Narrative Harness MVP Shipping Proof

This renews the release-cycle product-validation line after 0.12.0. The older
goals are retained as history; this document is the active 0.13.0 finish line.

0.12.0 proved that Guildhall could represent and close a bounded release using
Narrative Harness state. It did not, by itself, prove that Narrative Harness
was a useful, runnable story-intelligence MVP. 0.13.0 closes that gap without
turning Narrative Harness's domain concepts into universal Guildhall concepts.

## Copy/paste goal

> Ship Guildhall 0.13.0 by using Narrative Harness to produce and prove one
> real, runnable first release of Narrative Harness: a CLI-first, headless
> story drafting and evaluation MVP. Guildhall must make the release legible
> from source intake through capability shape, feature/task planning, exact
> execution, evidence, review, and shipment; Narrative Harness must produce
> useful outputs that survive its own quality checks.
>
> Re-intake Narrative Harness only from sources visible in Guildhall. Establish
> an honest project skeleton and one named release for the first MVP. That
> release must cover voice shaping, synopsis generation, story-world planning
> (including outline, characters, character voice, temporal facts, spatial
> facts, and other required context), chapter drafting in the selected author
> voice, and a review plan that tests the generated work. The review plan must
> include character-voice consistency, world and object-state continuity over
> elapsed time and environment, temporal continuity, spatial and geographic
> continuity, movement plausibility, plot/causal continuity, point of view and
> tense, pacing/structure, and other reviewer angles that the source-backed
> plan identifies as necessary. It must also prove how context is assembled,
> which reviewers participate, and how reviewer roles are combined or split to
> control token cost without dropping required coverage.
>
> Include a reproducible model bakeoff and provider decision in the release
> plan. Test viable DeepInfra or equivalent affordable model lanes for actual
> drafting and review quality across the supported genre matrix, including
> adult material where the selected provider and test fixture permit it. Record
> quality, consistency, latency, cost, failure behavior, and the reason for the
> chosen model or model set. The Narrative Harness release must use pnpm and
> expose reproducible CLI commands for its generation, review, and proof runs.
>
> Guildhall may reason about decomposition, sequencing, reviewer assignment,
> proof work, and release readiness, but it may not approve the owner's product
> decisions or broaden the selected release. Codex may perform explicitly
> delegated owner actions during this validation; that is separate from what
> Guildhall itself is allowed to automate.
>
> Treat every wrong count, invented capability, scraped prose bullet,
> ambiguous hierarchy, stale projection, hidden reviewer gap, generic proof,
> scope leak, false completion, slow read, oversized history, silent stall,
> or confusing action as a Guildhall defect first. Repair the shared model,
> authority, write path, projection, workflow, provider boundary, review plan,
> or UI component that owns the behavior; migrate affected state; remove
> competing machinery; add a focused regression; and replay the same release
> step. Do not make the proof pass with project-specific task edits, read-time
> synthetic records, duplicate business rules, fallback decomposition,
> permanent compatibility readers, manual database edits, or copy that hides
> uncertainty.
>
> Finish only when the installed Guildhall product and the Narrative Harness
> release both pass the acceptance gates below. A completed task tree, a Guildhall
> checkbox, a worker transcript, or a passing generic build is not an MVP. The
> result must be a reproducible Narrative Harness release artifact with durable
> proof, and a Guildhall release record that shows exactly what shipped and
> what remains later.

## What 0.13.0 is proving

```text
visible Guildhall sources
  -> honest NH project skeleton
  -> named MVP release
  -> executable capability and work tree
  -> reproducible CLI outputs
  -> reviewer evidence
  -> shipped NH release
  -> later NH scope remains separate
```

The NH release is a demanding product fixture. It is not permission to add
`voice`, `synopsis`, `character`, `world state`, or `adult` concepts to
Guildhall's general work model. Guildhall stores flexible work and proof;
Narrative Harness owns the story domain.

## Finite acceptance gates

### 1. Source becomes an honest MVP shape

Guildhall shows the NH purpose, audience, capability chain, selected release,
later scope, source trail, documented facts, inferences, and unknowns. It does
not promote architecture prose, transcript fragments, or arbitrary bullets to
deliverables without a bounded user outcome and proof expectation.

**Pass:** a first-time user can explain what the NH MVP does, what is in this
release, what is later, and what remains unknown without reading raw documents
or opening every task.

### 2. MVP shape becomes an executable release

The selected release has stable, complete, untruncated work identities,
hierarchy, membership, dependencies, ownership, proof contracts, and next
actions. Features, tasks, steps, proof, and review work may be nested to the
depth the actual scope requires. Splitting creates real child work and does
not leave recommendation or rewrite residue.

**Pass:** the Guildhall Map and Release views show the same capability chain,
scope, counts, progress, and later work after a cold restart.

### 3. The MVP actually runs

From a clean Narrative Harness checkout, pnpm commands can shape voice, produce
a synopsis, derive the required story context, draft at least one chapter, and
run the review plan. Outputs are saved as named artifacts with enough metadata
to reproduce the run, including model/provider, prompt/context-plan identity,
genre fixture, and version.

**Pass:** the release produces useful end-to-end output, not merely plans,
schemas, mock results, or passing unit tests.

### 4. Quality and model coverage are real

The release includes a model bakeoff and a genre fixture matrix. It records the
chosen model lane, cost/latency tradeoff, failure behavior, and quality result.
The evaluation covers the supported genre range, including an adult-compatible
fixture where the chosen provider permits it. Reviewer evidence covers voice,
world/object state, elapsed time and environmental effects, temporal continuity,
spatial/geographic continuity, movement plausibility, causal continuity, POV,
tense, pacing, and the additional source-backed lenses.

**Pass:** the review report can identify a real inconsistency, distinguish a
true failure from an acceptable creative choice, and show the newer passing
run that clears it.

### 5. Context and review orchestration are proven

The release records the context plan used for drafting, the facts supplied to
each agent, the reviewer roles that participated, and the reason for any role
combination or omission. Context is compact and intentional; raw transcripts
are not the proof surface.

**Pass:** a reviewer can explain why the chapter received the context it did,
which review angles ran, and where their evidence is stored.

### 6. Guildhall executes and ships the exact release

The selected release can be delegated-authorized by Codex, started, resumed,
paused, reviewed, proven, and closed without consuming later or unassigned NH
work. A deliberate proof failure is visible through the same owning item and
next action everywhere, then clears after newer evidence. The shipped release
stays shipped after restart and later-scope activation.

**Pass:** the Guildhall release record, CLI, API, Map, Overview, Work, Release,
Activity, Thread, and task detail agree on identity, scope, counts, status,
blockers, proof, next action, and shipment.

### 7. The user can understand the result

Project Map gives the 1,000-foot skeleton and release boundary. Overview gives
the current situation and next useful action. Work and detail show the exact
item and evidence. Primary actions lead to the item they name, stored titles
are never cropped, passive information is not styled as an action, and desktop
and mobile layouts remain readable.

**Pass:** fresh installed-app screenshots identify route, viewport, date, and
the claim they prove. Old calibration screenshots are not relabeled as release
evidence.

### 8. The product remains lean

Fleet reads use bounded projections, detail loads on demand, and essential
history contains decisions, transitions, proof references, and next actions.
Raw transcripts, context-debug payloads, and connection chatter remain bounded
operational evidence. The NH release proof does not reintroduce a heavy queue
or a second state authority.

**Pass:** installed startup, fleet/detail reads, NH state size, retained history,
and the release artifact size meet recorded budgets before and after the run.

## Finish line

Do not call 0.13.0 ready until all of the following are attached to the
release acceptance audit:

- a source-backed, user-legible NH MVP release;
- a reproducible pnpm CLI run producing synopsis, context, draft, and reviews;
- model bakeoff evidence and a documented provider/model decision;
- reviewer evidence for the named continuity, voice, spatial, temporal, and
  world-state dimensions;
- a deliberately failed and recovered proof;
- exact-scope execution, restart, release shipment, and later-scope proof;
- fresh installed-app desktop/mobile screenshots and API/CLI readback; and
- focused regressions, contract/data-layer checks, build/install/restart,
  `/api/stale-server`, and release package gates.

The 0.12.0 release-cycle proof remains valid as Guildhall product evidence. It
is not sufficient evidence that the full Narrative Harness MVP shipped. This
goal closes that specific gap.

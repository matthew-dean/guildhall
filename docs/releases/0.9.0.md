# Guildhall 0.9.0

Guildhall `0.9.0` is the release where the harness gets more serious about
trust. It moves project work toward managed runtimes, makes finished work prove
itself, gives memory a lifecycle, and lets MCP-aware outside agents read the
same project context Guildhall is using.

It is still a local macOS app. Your projects can be web apps, libraries, docs,
or native projects, but the Guildhall host for 0.9.0 is macOS.

## What changed

- **Runtime-backed execution:** Guildhall can run project work in an on-demand
  Podman runtime. The runtime starts when work needs it, mounts the project and
  host `~/.guildhall`, and leaves host-run compatibility available when setup
  is skipped or not ready.
- **Release-tied runtime image:** the 0.9 runtime image is published through
  GHCR as part of the same release set as the host package. The image contract
  names Debian 13 trixie, Node 22, Python 3.13, Playwright, runtime API
  version, executable shape, and immutable/minor-line tags.
- **Guided local runtime setup:** Settings -> Ready shows whether Podman is
  missing, installed but not started, ready, or unsupported. Guildhall does not
  install Podman or pull images during package install; setup is an explicit
  owner action.
- **Proof paths and completion handoffs:** done work now has a clearer proof
  trail: what was changed, how to launch or inspect it, which commands passed,
  what could not be verified, and what residue remains.
- **Memory lifecycle:** accepted project facts, habits, playbooks, global
  preferences, and Guildhall product ideas are separated so learned behavior is
  inspectable and reversible.
- **MCP context resources:** external agents can inspect project state,
  runtime, memory, context health, codebase knowledge, feedback, design context,
  and capability requests without scraping internal files.
- **Task shaping and flexible hierarchy:** Guildhall can split broad work into
  containing tasks and nested runnable tasks, then start or inspect the selected
  task instead of treating all work as one flat queue.
- **Design-quality proof:** UI work carries design taste, control semantics,
  preview/catalog context, owner feedback, and reusable-vs-local design
  findings so Guildhall aims for good results, not merely functional screens.
- **Review calibration:** review plans now carry risk lanes, calibrated recipes,
  required artifacts, and escaped-miss records. User-facing review can require
  screenshots or other evidence before a task is accepted.

## Why it matters

Guildhall is meant to turn a pile of thoughts into work you can trust. That
requires more than a worker loop. It needs a runtime boundary, enough evidence
to inspect the result, memory that explains why future agents behave
differently, and review that notices when "works" is not the same as "good."

0.9.0 is the foundation for that version of the product.

## The edges

The runtime path is guided and reversible. Host-run compatibility remains the
fallback when Podman is unavailable, unsupported, or not yet approved for a
project. The 0.9 docs snapshot is cut as part of the release process after the
package version and runtime image digest are finalized.
